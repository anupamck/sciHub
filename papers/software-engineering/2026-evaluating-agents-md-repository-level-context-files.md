## Why I saved this

- Relevance to my current work: this repo runs on an `AGENTS.md` file, and every agent vendor recommends writing one. This is the first study that actually measures whether that helps. The cost it establishes firmly; the benefit it fails to demonstrate. What it does change is what should go into such a file — instructions and genuinely non-redundant information, not a restatement of the README.

## Key points

- Main claim: providing a context file does not significantly improve coding-agent task success, but reliably increases cost. This holds across LLMs, agent harnesses, and for both LLM-generated and developer-committed files.
- LLM-generated context files caused a performance *drop* in 5 of 8 settings: −0.5% average resolution rate on SWE-bench Lite and −2% on CtxBench. Two-sided Cochran-Mantel-Haenszel p-values of 0.87 and 0.37 — no significant effect.
- Cost: context files increased average steps in every single setting (+2.45 on SWE-bench, +3.92 on CtxBench), producing a cost increase of 20% and 23% respectively. The body text reports this at p < 0.001%, but the appendix permutation tests (Table 6) are more varied — SWE-bench cost is < 0.00001, while CtxBench cost comes in at 0.00064 for generated files and 0.0126 for developer ones. Significant throughout, just not uniformly overwhelming.
- Developer-written files beat LLM-generated ones — +2.4% average resolution rate over no-context-file, and the LLM-vs-Dev comparison is the only significant accuracy result in the study (p = 0.038). Dev files helped every agent except Claude Code, despite not being written for any particular agent. They still cost up to 19% more.
- The asymmetry that limits the above: Dev vs **None** comes in at p = 0.21 — *not* significant. So the study can distinguish a hand-written file from a generated one, but never establishes that either beats having no file at all. The comparison that would justify writing a context file in the first place is the one that came out inconclusive.
- Repository overviews don't work *when the repo already has documentation*. Measured by "number of steps before the agent first touches a file the golden patch modifies," context files did not reduce time-to-relevant-file for any agent on either benchmark — and made it significantly *worse* for GPT-5.1 Mini.
- The overviews fail because they are **redundant**, not because agents don't need maps. When the authors deleted all documentation (`.md` files, example code, `docs/`) *after* generating the context file, LLM-generated files improved success by 2.7% on average and beat developer-written ones. The authors note this likely explains anecdotal reports that context files help — those come from niche repos with little documentation.
- The failure is not an instruction-following failure. When a context file mentions `uv`, agents use it ~1.6 times per instance vs. <0.01 when unmentioned; repo-specific tools go from <0.05 to 2.5 uses per instance. Agents obey — obedience just doesn't convert into solved tasks.
- What agents do instead: with a context file present they run more tests, grep more, read more files, write more files, and use more repo-specific tooling. More thorough, not more successful.
- Following a context file appears to make the task feel harder. Adaptive-reasoning models spend more reasoning tokens with a context file present: +22% for GPT-5.2 and +10% for GPT-5.1 Mini on SWE-bench.
- A concrete pathology in GPT-5.1 Mini traces: it issued extra commands to *find* the context file and then re-read it multiple times, despite the file already being in its context. This behavior only appeared when a context file existed at all.
- Overview sections are near-universal in generated files: a GPT-OSS-120B judge flagged overviews in 100% of Sonnet-4.5-generated files, 99% for GPT-5.2, 95% for Qwen3-30B-Coder — and only 36% for GPT-5.1 Mini. Of the 12 developer-written files, 8 had a dedicated overview and 4 enumerated directory structure.
- The three categories the authors found in most LLM-generated files: **Overview** (does it explain codebase structure), **Tooling** (environment setup, which tools to use), **Testing** (how to run the tests). Developer-written files shared no common categories — they were idiosyncratic, which is consistent with them encoding genuinely repo-specific information.
- Ablations rule out the obvious escape hatches: stronger generating models don't produce better context files (+2% on SWE-bench but −3% on CtxBench when a big model writes for a small one); neither the Codex nor the Claude Code generation prompt is consistently better, even for its own agent; and file length and task contamination fail to explain the null result.
- Removing individual categories (GPT-5.2) never significantly changed accuracy: CtxBench 68.12% with the full file vs. 62.32% without the overview (p = 0.15) and 63.77% without tooling (p = 0.31); SWE-bench 54.36% vs. 54.20% without the overview (p = 0.73). What removal *did* change was cost — dropping the testing section cut cost significantly on both benchmarks (p = 0.023 and 0.0035), and dropping tooling cut it on SWE-bench (p = 0.0012). Context files reliably change behavior without changing outcomes.
- How much the numbers bear: the results fall into two tiers. All six cost-and-steps comparisons are significant, though they span a wide range — from p < 0.00001 (SWE-bench cost) up to 0.0287 (SWE-bench steps) and 0.0126 (CtxBench cost for developer files). Every accuracy comparison, by contrast, is null or marginal (0.87, 0.37, 0.21, 0.038). The paper's secure contribution is the cost finding; the helpfulness question in its title is answered weakly. What strengthens the accuracy nulls is convergence rather than any single test — 8 settings, 4 models, 2 benchmarks and a battery of ablations all failing to find an effect is more persuasive than any one p-value.
- Limitations or caveats:
  - Python only — a language heavily represented in training data, so parametric knowledge of its tooling may already cover what a context file would say.
  - Only task resolution rate was measured; code efficiency and security were not.
  - Single sample per instance, and CtxBench's task descriptions and most of its unit tests are LLM-generated (though manually reviewed).
  - The Dev arm rests on **12 files**, one per repo, so repo difficulty is entangled with file quality.
  - The accuracy nulls are underpowered: 138 and 300 instances can only resolve large effects, so "not significant" does not mean "no effect."
  - p = 0.038 is marginal, and sits inside a large family of tests run across the paper.
  - The developer-written files were **never ablated**, so the headline advice to write only non-standard conventions is an extrapolation rather than a directly tested finding.
  - Dev vs LLM is confounded across authorship, content type and survivorship: those files had lived in real repos and been corrected over time, while the generated ones were made fresh and never used.

## Methodology

- Two complementary benchmarks, because neither alone can answer the question. SWE-bench Lite (300 tasks, 11 popular Python repos, none of which ship a context file) supports only the LLM-generated condition. So the authors built **CtxBench** to supply the developer-written condition.
- **CtxBench**: 138 instances mined from 5,694 PRs across 12 recent, niche Python repositories that all have a developer-committed `AGENTS.md` or `CLAUDE.md` at the root — including `ragas`, `tinygrad`, `smolagents`, `wagtail`, `fastmcp`, `pdm`, `ansible`, `opshin`, `openai-agents-python`, `pr-agent`, `graphiti`, `transformers`. Covers both bug fixes and feature additions.
- Five-stage construction: (1) GitHub search for repos with a root context file, filtered to Python + has test suite + ≥400 PRs; (2) filter PRs to those referencing an issue and modifying Python, judged by an LLM agent to introduce deterministic testable behavior; (3) an agent writes an environment-setup script that runs the test suite and dumps machine-readable results — 87% of filtered instances survived; (4) an LLM agent rewrites each issue into a standardized 6-section task description (description, steps to reproduce, expected behavior, observed behavior, specification, additional information) without leaking the solution; (5) an LLM agent generates unit tests, verified to fail pre-patch and pass post-patch, then manually reviewed to remove overfitting to the reference implementation. Final tests average 75% coverage of the modified code.
- Note the deliberate departure from SWE-bench: because niche repos often ship PRs with no tests, CtxBench *generates* the validating tests rather than requiring the PR to contain them.
- **Validating the Dev arm (§C)**: the developer-committed files were checked as genuinely human-authored, using Pangram's open-source AI-detection model plus length distributions. Developer files scored significantly less likely to be AI-generated, and tended to be *shorter* than the generated ones — the opposite of what you would expect if they were themselves `/init` output. This check is load-bearing, because many context files committed in the wild are themselves `/init` output; without it the Dev-vs-LLM comparison could quietly have been generated-vs-generated.
- **Three settings per instance**: `None` (context file removed, including developer files on CtxBench), `LLM` (generated with each agent's own recommended init command and model, run against the pre-patch repo state), and `Dev` (the developer-committed file from the pre-patch state — CtxBench only).
- **Agents × models**: Claude Code + Sonnet-4.5, Codex + GPT-5.2, Codex + GPT-5.1 Mini, Qwen Code + Qwen3-30B-Coder (served locally via vLLM). Temperature 0 everywhere except Qwen (0.7, top-p 0.8). Context file written to `AGENTS.md` for Codex and Qwen Code, `CLAUDE.md` for Claude Code.
- **Metrics**: success rate (all tests pass), number of steps (one environment interaction each), inference cost in USD, and — for behavioral analysis — tool-call frequency and reasoning token counts. Tool calls from shell commands were categorized by GPT-OSS-120B as an LLM judge, with categories built up iteratively from an empty set.
- **Controls against the null result**: the generating model was swapped (a strong model writing the file for a weaker one); the generation prompt was swapped between Codex and Claude Code; results were binned by file length; each of the three categories was deleted individually (using GPT-5.4) and re-run on GPT-5.2; and instances were split by whether the PR predates each model's knowledge cutoff, to test contamination.
- **The documentation-removal experiment** — the one that explains the overview null. Generate the context file as normal, then delete every `.md` file, all example code, and the whole `docs/` directory before running the agent, so the context file becomes the *only* documentation available. Claude Code was excluded from this arm for cost reasons.

## Notes

- The result is a specific instance of a pattern that keeps recurring in this vault: an intervention everyone assumes is beneficial, measured properly, turns out to be neutral or negative. Same shape as METR's productivity RCT, where developers *predicted* a 24% speedup and were actually 19% slower. Here the vendors predict a gain and the measurement finds a 20% cost increase for nothing.
- The overview finding is the actionable one, but it only holds with its condition attached. "Give the agent a map of the repo" fails not because agents can't use a map — it fails because the generated map restates the README sitting right next to it. Strip the documentation away and the map starts earning its place (+2.7%, and it beats the human-written file). So the rule isn't "no overviews," it's **no redundant content**.
- That reframing collapses both halves of the paper's advice into one principle: a context file earns its 20% cost premium only where it is the *sole* source of the information, and anything the agent can already read from the repo is being paid for twice. Instructions for non-standard practices, and overviews only where docs are absent, are the same rule. Worth flagging that this is an inference from converging evidence — the documentation-removal experiment plus the category ablation on generated files — and not a directly tested result, since the developer files were never ablated. This repo's own `AGENTS.md` fits the principle: the note-writing conventions and the template contract exist nowhere else in the repo.
- What the benchmark structurally cannot see (my reading, not a claim the paper makes): success is purely functional — all tests pass. CtxBench's tests were generated to pass for *any* implementation resolving the task and then manually de-overfitted, and the standardized task description carries its own specification section. So convention-conformance, precisely what the conclusion says context files *are* for, is largely invisible to the outcome measure. Partial counter: the repo's own passing tests are included in the final test set, so a project that gates conventions in CI would catch some violations.
- The precise finding is that steering works but doesn't convert. Instructions demonstrably land (`uv` from <0.01 to 1.6 calls per instance, repo-specific tools from <0.05 to 2.5), and agents become measurably more thorough. None of it moves pass/fail. Effective steering and *useful* steering come apart — a sharper claim than "context files don't work."
- The cost/behavior finding cuts both ways. Agents with a context file test more, explore more, and reason more — that's what you'd want from a careful engineer. It just doesn't move the pass/fail metric on these benchmarks. Whether more testing and exploration pays off on axes the paper explicitly did not measure (maintainability, security, code efficiency) is open, and the authors flag it as future work.
- The GPT-5.1 Mini "hunt for and re-read the file already in your context" behavior is a harness bug more than a content problem — a reminder that the delivery mechanism, not just the prose, has a cost.
- Follow-up ideas:
  - The paper's framing — instructions work, descriptions don't — is worth testing against skills, which are packaged instructions rather than repository descriptions. If the distinction holds, skills should land on the useful side of it.
  - Someone should run this evaluation on a non-Python, non-mainstream toolchain, which the authors name as the most likely place for context files to actually pay off.
  - "Rigorously evaluate before adoption" implies a per-repo A/B harness for context files. CtxBench is offered as the baseline methodology for that.

## FAQ

### Does the benchmark actually measure the thing context files are supposedly good at?
Largely not — and this is my reading rather than something the paper argues. Success is defined purely functionally: the patch is correct if the tests pass. CtxBench's tests were deliberately built to be shape-agnostic, generated to pass for *any* implementation that resolves the task and then manually reviewed to strip out anything overfitted to the reference patch. On top of that, the standardized task description carries its own specification section, so requirements that genuinely mattered for passing were handed to the agent in the prompt rather than left to the context file.

That means convention-conformance — style, design patterns, non-functional requirements, exactly what the paper's conclusion says context files *are* useful for — is close to invisible to the metric. A null result there was near-guaranteed by construction.

The overview null is different, and does not get this excuse. Navigation help should pay off on precisely the kind of task the benchmark does measure, and the authors probed that mechanism directly by counting steps before the agent first touches a file the golden patch modifies. It didn't improve for any agent on either benchmark. That is a real result, not a blind spot.

One partial counter to all this: the final test set includes the repo's own tests that pass on the fixed code, so a project that gates conventions in CI would catch some violations.

### What was actually in the Overview, Tooling and Testing categories?
The paper defines them only by a one-line probe question each — does the file explain the codebase structure (Overview), how do you set up the environment and which tools should be used (Tooling), and how do you run the tests (Testing). No sample file is published, but the rest of the paper fills in the picture.

Overview meant structural description, often literal enumeration: 8 of the 12 developer files had a dedicated overview section and 4 walked through directories and subdirectories. The generation prompts encourage this — Codex and Qwen Code instruct the agent to include an overview outright, while the Claude Code prompt asks for a high-level one only and warns against listing easily-discoverable components.

Tooling shows up in the trace analysis as package managers and project-specific commands: `uv`, `pip`, and per-project tooling. It is also the category with the clearest evidence of being read, since mentioning `uv` moves usage from under 0.01 to 1.6 calls per instance.

Testing meant test-invocation instructions, surfacing as `pytest`. It was the most expensive category — deleting it produced the largest cost drop of the three.

Important caveat: this taxonomy describes the **LLM-generated files only**. The developer-written files shared no common categories at all.

### If developer files share no common categories, what does comparing them against LLM files establish?
The two analyses never touch each other, which resolves the apparent mismatch. The category ablation ran exclusively on generated files (the paper says outright it could not do the same for developer files, since there were no shared categories to remove). The main Dev-vs-LLM comparison is entirely black-box: each file is an opaque blob, and only success rate, steps and cost are measured. So the conclusion drawn is narrow — files developers committed to their own repos produce better task success than files an agent generates via `/init` — and it holds regardless of what is inside either kind.

The absence of shared structure is itself evidence rather than a nuisance. Generated files are homogeneous and can only restate what they read from the repo; developer files are idiosyncratic, which is what you would expect if each encodes something not derivable from the code. The documentation-removal experiment then flips the ranking, which only makes sense if the generated files were carrying a duplicate of the docs while the human ones were carrying something else.

On the effect size, the paper quotes two figures that look inconsistent: the introduction says developer files beat generated ones by 7%, while §4.2 says they improve on no-file-at-all by 2.4%. These reconcile if the 7% is relative and the 2.4% is percentage points — generated files run about −2% against baseline, so the absolute gap is roughly 4.4 points, which against a ~60% base rate is about 7% relative. That arithmetic is mine, not the paper's; it does not state the units.

### How much should I trust these p-values?
Split them into two tiers. All six cost and step-count comparisons come out significant, spanning p < 0.00001 down to 0.0287, so the direction is not seriously in doubt: context files make runs longer and more expensive. Every accuracy result is null or marginal — 0.87, 0.37, 0.21, 0.038 — so the helpfulness question is answered far more weakly than the cost question.

The key misreading to avoid is treating "not significant" as "no effect." With 138 and 300 instances the study can comfortably detect a large effect but is nearly blind to a 2–3 point one, so several of these nulls are partly statements about sample size. What does strengthen them is convergence: many independent attempts all failing to find an effect carries more weight than any single test, even though no individual comparison is decisive. Note too that the one significant accuracy result sits inside a large family of tests, where roughly 1 in 20 clears the 0.05 line by chance alone.

Three tests appear in the paper. Cochran-Mantel-Haenszel compares success rates while holding repo strata fixed, so a couple of easy repos cannot drive the answer. McNemar's test handles the paired ablations, looking only at tasks where the two conditions disagreed. A permutation test handles cost, since cost data is skewed by a few expensive runs and suits an assumption-light method.
